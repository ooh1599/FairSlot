# Draw algorithm, manifest format and failure policy (v1)

Implemented twice: `contracts/FairSlot.sol` and `shared/draw.ts`. Both must produce identical output; `docs/golden-vectors.json` holds the fixed vectors and both test suites assert them.

## Canonical manifest (schemaVersion 1)

Serialization (`shared/canonical.ts`):

- JSON, no whitespace between tokens, encoded as UTF-8.
- Every string (values and keys) is Unicode-normalized to **NFC** first.
- Object keys sorted ascending by UTF-16 code unit (all FairSlot keys are ASCII). Arrays keep their order, which is meaningful.
- Only strings, booleans, `null` and safe integers. Floats, `undefined` and duplicate keys (after normalization) are rejected.
- Hash: **keccak256** over the UTF-8 bytes, shown as lowercase `0x` hex.

Fields: `schemaVersion`, `eventPublicId`, `title`, `description`, `rules`, `organizerWallet`, `chainId`, `contractAddress`, `drawNotBeforeUtc` (ISO-8601, whole seconds, `Z`), `algorithmVersion`, `randomnessFailurePolicy`, `participantCount`, `winnerCount`, `reserveCount`, `prizes` (rank 1..winnerCount), `entries`.

`entries` holds only random public entry IDs (60 random bits, Crockford base32, e.g. `7K3M-9QX2-H4TD`, generated by the database), **sorted ascending**. The index of a person is therefore fixed by the random IDs, not chosen by the organizer. Names, emails and contact data never enter the manifest, and no ID is derived from an email or phone.

Storage: `manifests/<eventPublicId>/<hash>.json` in a public Supabase bucket. The file name is the hash and uploads use `upsert: false`; the app has no update or delete path, and storage policies grant no client write access. The onchain record keeps `manifestHash` and `manifestURI`. A hash proves the file matches; it does not promise the file stays online, so the UI says so and offers downloads.

## On-chain identifiers

- `eventId = keccak256(abi.encode(chainId, contract, organizer, keccak256(utf8(eventPublicId))))`. Including the organizer prevents another account from squatting an ID.
- `clientSeed = keccak256(abi.encode(keccak256("FairSlot/clientSeed/v1"), chainId, contract, eventId, manifestHash))` is sent to the coordinator, so the frozen list is part of the request itself.

## Winner selection

Let `n` = participantCount, `K` = winnerCount + reserveCount (`K <= 50`, `K <= n`).

```
base      = keccak256(abi.encode(keccak256("FairSlot/draw/v1"), chainId, contract, eventId,
                                 manifestHash, requestId, randomWord, algorithmVersion))
candidate = keccak256(abi.encode(base, uint32 position, uint32 counter))

uniform(position, range):                # range = n - position
  if range == 1: return 0                # consumes no hash
  rem = 2^256 mod range
  for counter = 0, 1, 2, ...:            # rejection sampling, no modulo bias
    h = candidate(position, counter)
    if h <= 2^256 - 1 - rem: return h mod range

for p in 0..K-1:                          # partial Fisher-Yates, sparse swap map
  j  = p + uniform(p, n - p)
  vp = swap[p] or p
  vj = swap[j] or j
  if j != p: swap[j] = vp
  winners[p] = vj
```

- Positions `0..winnerCount-1` are main winners, the following `reserveCount` positions are reserves, from the same word. Prize `k` goes to main winner `k`. Reserves are called in order; nobody is re-drawn.
- `randomWord` is the single `bytes32` the coordinator delivers. It is never combined with anything the caller can choose.
- `finalize(eventId, maxPositions)` is permissionless, takes 1..25 positions per call, and resumes from stored progress. Batch size cannot change the result (tested with sizes 1, 3, 7 and 25 over the same event).
- Work per transaction is bounded: 25 positions cost about 0.78M gas at `n = 10,000` (measured), so 50 picks need at most two transactions. No limit beyond the product limits (10,000 entries, 50 picks) was needed.
- The coordinator callback only stores the word and flips the state (about 76k gas including the test mock; the requested callback gas limit is 150,000).

Forbidden as randomness (and not used): `Math.random`, `Date.now`, `block.timestamp`, `blockhash` alone, `prevrandao` alone, any server-chosen seed.

## State machine

```
(DRAFT is off-chain only)
COMMITTED -> RANDOMNESS_REQUESTED -> RANDOMNESS_RECEIVED -> FINALIZING -> FINALIZED
COMMITTED -> CANCELLED                      (organizer only, before the request)
RANDOMNESS_REQUESTED -> FAILED              (no accepted proof; see below)
```

- Organizer, manifest hash, counts, algorithm version and times are written once at commit and never changed.
- Only one accepted request per event; the callback checks the sender (coordinator) and that the request ID belongs to that event, and in the right state.
- No admin, no upgrade path, no function that writes winners other than `finalize`.

## Failure policy

| Situation | What happens |
| --- | --- |
| Proof accepted, callback failed | State stays `RANDOMNESS_REQUESTED`; `markFailed` refuses while the request is `fulfilled`. Anyone calls the coordinator's `retryCallback` with more gas. The **same** word is redelivered. No new request is ever made. |
| No accepted proof by the 60 s deadline | `markFailed` (anyone) or the coordinator's `refundRequest` (anyone; its `onRefund` hook closes the event) ends the event as `FAILED`. No automatic re-roll, no provider switch. |
| Proof accepted after a slow callback | Not failed: only `!fulfilled` requests can be failed. |
| Cancel after the request | Not possible (state check), so a bad draw cannot be dodged. |

Refund recipient is fixed at commit (`refundRecipient`) and passed to the coordinator as its refund address. FairSlot never holds funds: `requestDraw` pays the exact fee quoted inside the transaction and returns any surplus to the organizer in the same call. Any refund credit left at the coordinator can be pulled only by that recipient (`withdrawRefundCredit`), and the UI shows a withdraw button when a credit exists.

## Things this system does not claim

- It does not prevent one person from entering several times, and does not prove participants are real people.
- It does not guarantee a provider responds; it guarantees the outcome of an accepted request cannot be changed.
- It does not deliver or escrow prizes.
